### 2.5 Feature-Selector MP-EM-RAM

mass. The follow-up experiment should use continuous feature weights rather
than hard selection.

### 2.6 Feature-Weight MP-EM-RAM

Job id: `9092317`.

Config:
`longlive/methods/motion_projected_em_ram/configs/skateboarding_motion_projected_em_ram_feature_weight.yaml`.

Implementation: replace the hard feature gate with continuous CoTracker
component weights. Mean normalization keeps the update mass near the full
MP-EM-RAM run:

```yaml
feature_selector_mode: component_weight
feature_weight_direction_center: 0.0
feature_weight_direction_temperature: 0.25
feature_weight_speed_penalty_coef: 0.25
feature_weight_min: 0.25
feature_weight_max: 1.5
feature_weight_normalize_mean: true
subspace_mode: coarse_motion
```

Training diagnostics:

- total train setup: 78.5s; train loop: 1790.9s.
- unlike hard gating, update mass did not collapse at outer 5:
  `alpha=0.146`, `w=0.993`, `shift=697.7 -> 359.2`.
- later EM positive excess still became small (`alpha=0.013` at outer 8), but
  this was not caused by the feature weights (`w=1.000`).

| dataset | app_div | temp | pick | motion_fidelity | dynamic_score | dynamic_rate |
|---|---:|---:|---:|---:|---:|---:|
| UCF | 25.757 | 0.952 | 20.852 | **0.221** | 10.091 | 0.650 |
| LOVEU | 26.293 | 0.943 | 21.156 | **0.268** | 8.506 | 0.368 |

| run | VBench Total | Quality | Semantic | Dynamic |
|---|---:|---:|---:|---:|
| feature-weight MP-EM-RAM | **83.801** | **85.652** | 76.398 | **93.056** |

Conclusion: continuous component weights fix the internal sparsity pathology
of hard feature gating, but not the objective mismatch. Because the weights are
mean-normalized, a rollout group that is bad in absolute motion reward still
keeps roughly full update mass. The result is high dynamic_score but poor
motion_fidelity, i.e. more motion artifact rather than better motion match.
The very high VBench dynamic degree should therefore be treated as an artifact
warning, not as evidence of better motion consistency.

### 2.7 Score-Weight MP-EM-RAM

Job id: `9092667` (submitted after feature-weight motion_eval confirmed
failure; VBench pending at the time of this note).

Config:
`longlive/methods/motion_projected_em_ram/configs/skateboarding_motion_projected_em_ram_score_weight.yaml`.

Implementation: keep EM's relative KL tilt, but multiply the M-step alpha by a
soft absolute reward feasibility weight:

```yaml
feature_selector_mode: score_weight
feature_score_center: 0.0
feature_score_temperature: 0.25
feature_score_min: 0.0
feature_score_max: 1.0
feature_score_normalize_mean: false
```

The intended fix is not another scalar reward sweep. It changes the EM
interpretation: group-best endpoints are not necessarily feasible M-step
targets. If all sampled endpoints have poor absolute motion reward, the correct
M-step is to stay close to the anchor rather than preserve update mass.

Training diagnostics:

- setup time: 80.1s; train loop: 1898.7s.
- absolute score weights behaved as intended: bad rollout groups had small
  update weights (`w=0.114`, `0.265`, `0.304`), while good groups kept large
  update weights (`w=0.858`, `0.931`).
- the mechanism avoided feature-weight's full-mass artifact mode, but it
  became too conservative.

| dataset | app_div | temp | pick | motion_fidelity | dynamic_score | dynamic_rate |
|---|---:|---:|---:|---:|---:|---:|
| UCF | 25.691 | 0.971 | 21.318 | **0.260** | 3.518 | 0.017 |
| LOVEU | 26.567 | 0.964 | 21.551 | **0.323** | 3.260 | 0.020 |

| run | VBench Total | Quality | Semantic | Dynamic |
|---|---:|---:|---:|---:|
| score-weight MP-EM-RAM | 82.868 | 84.340 | **76.976** | 50.000 |

Conclusion: score-weighting corrected the previous artifact failure, but it
over-rejected motion. The result is lower motion_fidelity than full MP-EM-RAM
and much lower dynamic_score than the baseline. VBench confirms the same
diagnosis: dynamic degree returns to the baseline level rather than improving,
while Total/Quality drop below full MP-EM-RAM. The next variant should not use
the mixed scalar reward as the absolute acceptor; it should gate M-step updates
with decomposed motion components and keep a small trust-floor update for
efficiency.

### 2.8 Component-Feasibility MP-EM-RAM

Job id: `9094046`.

Config:
`longlive/methods/motion_projected_em_ram/configs/skateboarding_motion_projected_em_ram_component_feasibility.yaml`.

Implementation: reuse `component_weight`, but make it an absolute feasibility
gate rather than a mean-normalized redistribution:

```yaml
feature_selector_mode: component_weight
feature_weight_direction_center: 0.0
feature_weight_direction_temperature: 0.25
feature_weight_speed_penalty_coef: 0.25
feature_weight_min: 0.25
feature_weight_max: 1.0
feature_weight_normalize_mean: false
subspace_mode: coarse_motion
```

Rationale: feature-weight failed because bad rollout groups still preserved
full update mass; score-weight failed because scalar reward feasibility became
too conservative. Component-feasibility keeps the absolute no-normalization
property, but applies it to direction/speed components and leaves a small
floor so adaptation does not stall.

Training diagnostics:

- setup time: 78.5s; train loop: 1793.3s.
- negative-reward rollout groups kept small but nonzero update mass, e.g.
  `w=0.287`, `0.380`, `0.348`, `0.387`.
- good-direction groups kept larger update mass, e.g. `w=0.726`, `0.842`.
- this is the intended middle ground between feature-weight's full update mass
  and score-weight's near-stalled updates.

| dataset | app_div | temp | pick | motion_fidelity | dynamic_score | dynamic_rate |
|---|---:|---:|---:|---:|---:|---:|
| UCF | 26.107 | 0.970 | 21.288 | **0.319** | 5.743 | 0.117 |
| LOVEU | 27.112 | 0.961 | 21.500 | **0.359** | 5.268 | 0.099 |

| run | VBench Total | Quality | Semantic | Dynamic |
|---|---:|---:|---:|---:|
| component-feasibility MP-EM-RAM | **83.303** | **84.905** | **76.898** | 63.889 |

Conclusion: component-feasibility recovers most of full MP-EM-RAM's
motion_fidelity while avoiding feature-weight's artifact-level dynamic scores
and score-weight's over-conservative low-dynamic behavior. It is not better
than full MP-EM-RAM, but it is a cleaner stable point for efficiency tests:
motion_eval is close to the stable family, VBench is above the paper baseline,
and dynamic degree is increased without reaching artifact-level values.

but reduce only the number of outer on-policy anchors:

## 3. Interpretation

Current evidence separates three objectives:

1. **Do not collapse distribution**: RAM and MP-EM-RAM satisfy this. NFT-H3 /
   H3' and DRaFT-K did not.
2. **Increase visible motion / dynamic degree**: baseline-relative and
   reference-motion variants can do this.
3. **Match reference motion**: none of the recent variants fully solve this;
   hard reference projection and hard feature gating both reduce
   motion_fidelity, and hybrid projection only partially recovers it.

The most useful next step is not another scalar reward tweak. The optimization
problem should explicitly encode:

```text
motion consistency is the protected direction;
appearance / color / pixel residuals are allowed to move or blur.
```

The strongest next variants should therefore use **soft / mixture update
subspaces and soft feature weights**:

```text
update = coarse_motion_component
       + lambda_ref * reference_motion_component
       - lambda_orth * appearance_orthogonal_penalty

or

alpha_i <- alpha_i * soft_motion_consistency_weight_i
```

rather than replacing the update with a hard reference-motion projection or a
binary endpoint gate. The first hybrid run validates the mixture mechanism but
suggests the reference subspace itself should come from a stronger motion
representation than latent temporal differences. The feature-selector run
suggests the reward-feature signal is useful, but should modulate update mass
continuously instead of zeroing samples. The feature-weight run then shows the
opposite failure: preserving update mass for globally bad groups is also wrong.
The current score-weight run therefore adds an absolute feasibility term to the
EM M-step. Its motion_eval result shows that absolute feasibility is necessary
but not sufficient: using the scalar reward as the feasibility variable
over-suppresses motion. The follow-up component-feasibility run keeps absolute
gating while separating direction consistency from scalar reward acceptance.
